# wizard-toggle-parse: e2e test

Tier 1 of the harness, the pre-commit gate. Seconds, no container, nothing installed.

Section headings sit at level two because the `e2e-runbooks` test-spec template fixes the seven section names at that level, which overrides this repository's level-three heading rule.

The capability is named after the wizard parse check because that is the defect the tier was built around, but the gate command runs every tier 1 check and cannot run one alone. All of them are covered below.

---

## What this verifies

- Both wizards read the same toggles out of the same YAML. For each of `group_vars/all.yaml`, `linux.yaml`, `macos.yaml` and `windows.yaml`, the key and state set that `read_boolean_toggles` in [../../setup/setup.sh](../../setup/setup.sh) emits equals an independent parse of the file, and the key set that [../../setup/setup.ps1](../../setup/setup.ps1) matches equals the key set bash emits. This exists for the "Wizard toggle parse desync" entry in [../../docs/regression_ledger.md](../../docs/regression_ledger.md): an end-anchored state substitution let any toggle carrying a trailing comment reach the caller unconverted, so 11 toggles on Linux and 4 on macOS rendered unchecked with a stray colon in the label and could not be controlled in either direction, while the PowerShell wizard was never affected.
- No toggle is dropped or malformed on the way from the YAML to the wizard. Every emitted line has the shape `<key> ON|OFF`, no emitted key carries a colon, and the emitted count matches the independent count. The desync entry above produced the variable name `install_tailscale:=false`, which Ansible accepts silently and which leaves the real toggle untouched.
- Every enabled toggle resolves to something that installs it, per OS family. For Debian, RedHat, Archlinux, Darwin and Windows, each toggle whose effective value is true either has a `software_mapping` entry in `vars/<family>.yaml`, or is referenced as `install_<key>` by a role task file or by `site.yaml` with comments stripped, or is listed for that family in [../tier1/documented_no_ops.txt](../tier1/documented_no_ops.txt). This exists for the "Toggles enabled with no mapping and no task" entry in the ledger, where `install_putty` had no mapping on Arch or Fedora and `install_gradle` had none on Debian or Fedora behind a comment claiming SDKMAN handled it, and for the "Toggles that had already been dead for a while" entry, where four toggles appeared ticked in the wizard with no working install path on any operating system.
- The documented no-op list stays honest. No line in it forgives a toggle that has since gained a real mapping, because a stale entry makes a later break in that mapping look intentional.
- The four Windows system settings resolve too, which `install_` coverage cannot see. Every key [../../setup/windows/WindowsSettings.ps1](../../setup/windows/WindowsSettings.ps1) claims is a real boolean toggle in the `group_vars` pair the Windows wizard reads, every system-setting toggle that wizard shows is claimed by that file, every claimed key is applied by its dispatch, and the nine optional features it enables are declared once in that file, led by the two WSL 2 needs, handed unchanged to the applier, and returned unchanged by the accessor a checker asks. The Ansible task file that used to be the second list has been deleted with the rest of the unreachable Windows Ansible, so what remains is the same two-lists shape as the wizard desync above, held between the declaration and the accessor, and the coverage half is the non-install remainder of the "Toggles enabled with no mapping and no task" entry: a system setting has no `vars/Windows.yaml` mapping it could ever resolve to, so its only possible consumer is that file.
- The verification only looks, and something actually runs it. [../../setup/ansible/verify_install.yaml](../../setup/ansible/verify_install.yaml) uses no module that can change the machine and marks every `command` and `shell` read `changed_when: false`, [../tier3/verify.yaml](../tier3/verify.yaml) imports that play instead of holding a second copy of its assertions, and [../../setup/setup.sh](../../setup/setup.sh) ends both of its run paths in the verification, hands it the same selection it handed the playbook, and runs it under a stdout callback that cannot truncate the run's own logs. This is the "toggle nothing consumes" shape from the ledger applied to a whole step: a verification the wizard forgets to run, or one that resolves the selection a second time and demands the applications the user unticked, reports on a machine nobody asked about.
- The pinned versions and download locations stay behind one reader, and every one of them still has a reader. Nothing under [../../setup/](../../setup/), [../](../) or [../../docs/manual/](../../docs/manual/) reads the pins file or resolves a `{{ ref }}` except [../../setup/pinned_values/pinned_values.py](../../setup/pinned_values/pinned_values.py), every pin is reached by a reference in the playbook, by a name the dispatcher builds from an `apt_url` or `dnf_url` mapping key, by another pin, or by name from a script, every such reader names a pin that exists, every resolved value is a non-empty string with no brace left in it, no pin name is defined as a variable anywhere else in the repository, and the PowerShell adapter and the reader agree key by key. This exists because the YAML this replaced had three separate hand-written parsers, and they drifted: the Windows one left an unresolvable reference standing as literal text and the `sed` one in `windows_mapping` could follow exactly one hop. The precedence assertion is the one with no history behind it yet: the pins used to arrive as a play `vars_files` entry, rank 14 of 22, and now arrive from a vars plugin, ranks 4 to 10, so a same-named variable elsewhere would now win where it previously lost.
- The playbook parses, and parses quietly. `site.yaml` and [../tier3/verify.yaml](../tier3/verify.yaml) both pass a syntax check, the syntax check emits at most two warnings, and no repository file is reported as an inventory source. This exists for the ledger entry on `ansible.cfg` setting `inventory = localhost,`, where the empty entry after the comma resolved to the config directory, Ansible walked all of `setup/ansible/` as an inventory source, and 212 warnings printed on every invocation without an explicit `-i`. A real warning cannot be seen in that.

## Prerequisites

Confirm the shell is Linux. On Windows this means running from inside WSL, which is also the only place Ansible runs at all.

```bash
uname -s
```

Expect `Linux`. Anything else and the harness refuses tiers 2 and 3 outright, and the tier 1 scripts depend on GNU tool behaviour that Git Bash does not reliably provide.

Confirm `ansible-playbook` is on PATH.

```bash
command -v ansible-playbook
```

Expect a path. Without it the static check exits 2 before running any assertion.

Confirm GNU grep, because the cross-wizard comparison uses a Perl-mode pattern to pull the toggle regex out of the PowerShell wizard.

```bash
grep -V
```

Expect the first line to name GNU grep. With a grep that lacks `-P`, the cross-wizard comparison is skipped with a warning rather than failed, so the run would pass while covering less than it claims.

Confirm the working tree holds exactly the change you intend to test.

```bash
git status --short setup e2e
```

Expect only your own edits. Tier 1 asserts against the working tree, not against a commit, so an unrelated half-finished edit under [../../setup/](../../setup/) becomes part of the input.

Note whether yamllint is installed, because it changes the assertion set.

```bash
command -v yamllint
```

Either answer is acceptable. When it is present, a yamllint finding under `setup/ansible/` is a failure. When it is absent, that assertion is skipped with a warning and the run covers less.

## Reset state

None. This test writes no persisted state. It reads the working tree, extracts two functions out of `setup.sh` and evaluates them inside its own shell rather than launching the interactive wizard, and starts no container.

One side effect worth knowing: `ansible-playbook --syntax-check` writes into `~/.ansible/tmp` and the fact cache under `~/.ansible/`, because [../../setup/ansible/ansible.cfg](../../setup/ansible/ansible.cfg) moves those paths out of `/tmp`. Nothing in the repository is touched.

---

## Run

Run the gate from the repository root. With no arguments it is tier 1 only.

```bash
./e2e/run.sh
```

From a PowerShell prompt on Windows, the same run inside WSL.

```powershell
wsl -d Ubuntu bash -c "cd /mnt/d/Development/projekty-IT/InstallationHelper && ./e2e/run.sh"
```

Wait for the process to exit. It runs the checks in order and does not stop at the first failure, so the whole output is meaningful even when something fails early.

## Expected

The process exits 0. A non-zero exit means at least one check failed, and the harness prints the failing check names under a per-script tally line. Each script reports its own tally with the shape `<label>: N checks, all passed`, so a script that fails still tells you how many assertions ran.

Seventeen check scripts run, in this order, and the list below is the whole of tier 1. Each is named by its script so [../tier1/verify_spec_parity.sh](../tier1/verify_spec_parity.sh) can read `run_tier1`'s own loop and prove this section is complete. Per-script assertion counts are deliberately not stated, because they grow as checks are added and a stale number here would be worse than none.

1. `wizard_parse` reports five passes for each of `all.yaml`, `linux.yaml`, `macos.yaml` and `windows.yaml`: the bash parse matches the YAML with a toggle count, every emitted line has the shape `<key> ON|OFF`, no key carries a stray colon, no toggle is dropped between the YAML and the wizard, and the two wizards see the same toggle keys. A mismatch prints a truncated diff of the two key sets rather than a log excerpt. Two further passes cover the whole set rather than one file: every visible system setting has a descriptive label, and both wizards hide the same toggles.
2. `toggle_coverage` reports one pass per OS family, `Debian`, `RedHat`, `Archlinux`, `Darwin` and `Windows`, each stating how many enabled toggles resolved. A failure names the unresolved toggles. One further pass states that the documented no-op list has no stale entries, and a failure names each family and toggle pair that is forgiven while a real mapping now exists. Windows is judged differently from the other four: a Windows-gated Ansible task cannot run, so only the three native installers count as coverage there. Four more passes cover the `apt_url` and `dnf_url` mappings, two per family: that every one has a download location, meaning an inline `url:` field or a non-empty `<key>_url` asked of the pinned values port, and `<key>_rpm_url` as well on Fedora, and that every one names the package the way dpkg or rpm will report it rather than holding a filename or a URL. Both dispatch tasks skip silently when the location renders empty, and the verify play looks the installed package up by that name, so a filename there means the check can never pass.
3. `profile_prerequisites` reports that the toggles whose only Linux install path is npm were derived from the task graph rather than written down, and then one pass per file in `profiles/`: a profile that turns `install_nodejs` off must turn every one of those toggles off with it. `profiles/linux_live.yaml` turned off five of the six and left `install_bruno_cli` on, which group_vars/all.yaml has enabled, so every live-profile run failed on all six distributions with the npm helper reporting NVM absent. The derivation follows the includes the way Ansible does, from whatever includes `npm_install_unix.yaml` up one level to the toggle that guards it, so a seventh npm tool added later is covered without editing this check. It reports SKIP without a Python 3.11 or newer on PATH, the same way `manifests` does, because the walk needs one.
4. `timeout_indirection` reports that `ih_timeout` is set as a fact before any role runs, that it names `gtimeout` as well as `timeout`, that `macos_core` installs the coreutils package which provides `gtimeout`, and that no task line calls the bare command at a command position. macOS has no `timeout`: it is GNU coreutils and the BSD userland does not ship it, so all twenty-seven call sites failed there with "timeout: command not found" and the macOS run died at the first, in `sdk_manager`, taking Node, pyenv, SDKMAN, FVM, the Android SDK, the npm tools and JetBrains Toolbox with it. None of them was wrong on Linux, which is why it survived until the first stage 3 run. The fix is a convention rather than a mechanism, so this exists to stop the twenty-eighth call site being written the old way, working on every Linux run and failing on every Mac. Comment lines are excluded, because the reasoning beside several of those tasks names the command in prose.
5. `windows_mapping` reports that every mapping-shaped line in `vars/Windows.yaml` parses in bash, that the PowerShell installer parses the same number of mappings, that the two agree on every mapping including manager and source, that every mapping has a toggle to select it, and that the Windows Python mapping still matches `default_python`. The PowerShell half needs a runnable `pwsh`, which on this machine means running the gate from Git Bash rather than WSL, and it reports SKIP rather than passing quietly when it cannot. Locating that `pwsh` and converting a path for it live in [../tier1/pwsh_probe.sh](../tier1/pwsh_probe.sh), shared with the next-but-one check, because the probe has to reject the Microsoft Store alias stub and a second hand-written copy of that would be the one that rots.
6. `windows_npm_parity` reports that the native npm tool list and the `ai_tools` role's Unix task files name the same packages, and that every one has an install toggle. The reference used to be the role's Windows task files, which have been deleted with the rest of the unreachable Windows Ansible. The Unix ones are the better reference anyway, because they execute: a Windows package that has drifted from the one Linux and macOS install is a real difference in what the user gets.
7. `windows_settings` reports that [../../setup/windows/WindowsSettings.ps1](../../setup/windows/WindowsSettings.ps1) still exports both of the lists this check asks it for, that those nine optional feature names are declared once in the file, led by the two features WSL 2 needs, and passed unchanged to `Enable-WindowsFeatureSet` at every call site, that the accessor returns that declaration in its order, that all three setting keys are boolean toggles in the `group_vars` pair the Windows wizard reads, that the visible non-`install_` toggle set in that pair is exactly those three keys, and that each one is applied by `Invoke-WindowsSystemSetting`. The two lists are asked of the file through `Get-WindowsOptionalFeatureName` and `Get-WindowsSettingKey`, so the check sees what the applier sees rather than a parse of the dispatch, and it reports SKIP without a runnable `pwsh` the way `windows_mapping` does. The accessor assertion and the declaration assertion are the two deliberately written in bash, so a SKIP cannot hide either the accessors' deletion or a second feature list appearing at the call site. The comparison used to be against `windows_core/tasks/windows_features.yaml`, which has been deleted along with the rest of the unreachable Windows Ansible, so the second list is now the file's own declaration. It also carries the non-`install_` half of Windows toggle coverage, which `toggle_coverage` cannot reach: a system setting has no `vars/Windows.yaml` mapping and no runnable task, so this file is its only possible consumer, and the set comparison closes the gap in both directions instead of teaching `toggle_coverage` a second Windows special case. The `group_vars` pair is `all.yaml` overlaid by `windows.yaml`, because `set_custom_wallpaper` is cross-platform and lives in `all.yaml` while the other two are Windows-only. There were four until 2026-08-22, when the nightly hibernate task was removed at Lukk's request: he does not want the machine hibernating on a schedule, and a hosted runner cannot hibernate at all, so the feature was deleted rather than suppressed.
8. `verify_spec_parity` reports that every assertion in the verification play, [../../setup/ansible/verify_install.yaml](../../setup/ansible/verify_install.yaml), is named in each of the five container capability specs, and that this spec names every tier 1 check script. It reads the play rather than [../tier3/verify.yaml](../tier3/verify.yaml) because the play is where the assertions live: the tier 3 file is a wrapper that imports it, so a container run and a real machine assert the same eleven things. It is the check that keeps this document honest, and it fails when a spec understates what its run proves.
9. `verify_wiring` reports that the verification play uses no state-changing module, that every one of its `command` and `shell` reads is marked `changed_when: false`, that [../tier3/verify.yaml](../tier3/verify.yaml) imports the play instead of carrying assertions of its own, that both of the wizard's run paths end in `finish_run` and therefore verify, that the verification is handed the same selection as the playbook by slicing it off `PLAYBOOK_ARGS` rather than resolving it a second time, and that it runs under the stock stdout callback. Each guards a defect with a known shape. A play that installs something is no longer a diagnostic, and a person is told to run this one on a working laptop. A verification wired into only one entrypoint leaves the scripted install, the one nobody watches, reporting success without ever asking the machine. A second resolution of the selection drifts from the first, and the drift demands every application the user unticked and reports it missing. And `dual_logger` opens the four `installation_*.log` files with mode `w`, so verifying a run under it would erase that run's own log.
10. `failed_key_reads` reports that nothing in the playbook, the task files it imports, the profile overlays, its roles or the verify play decides anything from a result's `failed` key. It exists for one defect that cost a day: a collector selecting on `failed == true` could never match, because the task that registered the result carried `failed_when: false` and Ansible applies `failed_when` by rewriting that very key. Three AUR builds that exited rc 1 were counted as successes. `rc` and `finished` survive `failed_when` untouched and are what to read instead. Five shapes are matched: `selectattr` or `rejectattr` on the key, `attribute="failed"`, dotted access on a word boundary, bracket access, and the Jinja tests `is failed` and `is not failed` with their `failure` alias. The word boundary is what catches `when: r.failed` and `failed_when: r.failed == true`, the two shortest ways to write the forbidden thing, both of which an earlier version of the pattern passed because it required a pipe or a closing brace straight after the key. `until: <result> is succeeded` is deliberately not matched, because forty tasks use it as their retry condition and a forty-line allowlist forgives by default rather than by decision. Exceptions live in [../tier1/failed_key_reads_allowed.txt](../tier1/failed_key_reads_allowed.txt), currently empty.
11. `tolerated_failures_read` reports how many tasks tolerate failure and how many of those register a result, that every registered result is read somewhere other than its own register line, and that the allowlist has no stale entries. It exists for the second half of the same defect the check above guards: a task tolerates failure, registers a result, and nothing downstream reads it, so the tolerance is real and the reporting is imaginary. A registered variable nobody uses is legal Ansible, so nothing warns. The scan also refuses to report on fewer than ten tolerated tasks, because a block-splitting pattern that stops matching would otherwise pass every assertion. Exceptions live in [../tier1/tolerated_failures_allowed.txt](../tier1/tolerated_failures_allowed.txt), currently empty, because the one candidate was a diagnostic whose register was simply dead and was removed instead.
12. `os_family_derivation` reports that the playbook branches on the derived family rather than on Ansible's own answer, and that the derivation resolves every distribution this repository claims to support. It exists because Ansible maps a distribution to a family through one fixed table in `ansible/module_utils/facts/system/distribution.py` and falls back to the distribution's own name for anything absent from it, so on a derivative such as Nobara every `os_family == '...'` condition here was false, no `vars/<family>.yaml` matched, and the run stopped having installed nothing. Eight passes: that [../../setup/ansible/tasks/derive_os_facts.yaml](../../setup/ansible/tasks/derive_os_facts.yaml) still reads `/etc/os-release` and still sets both `ih_family` and `ih_base`, which is what stops the exemption below from becoming vacuous; that `site.yaml` imports it before the OS dictionary named after it is loaded, with both line numbers in the message; that no task file under `setup/ansible` reads `ansible_facts['os_family']` or the raw distribution name; that no entry in [../tier1/os_family_reads_allowed.txt](../tier1/os_family_reads_allowed.txt) has gone stale, each entry forgiving one exact line rather than a whole file; that every os-release fixture is named by a case and every case has a fixture; and three from a real Ansible run of the shipped derivation against those fixtures, that it asserted one case per fixture, that every fixture derives the expected pair with openSUSE rejected rather than silently treated as RedHat, and that the machine running the gate resolves to a supported family. The play carries one case with no fixture, because the absence of the file is its input: a path that does not exist, standing in for macOS and Windows, where both facts must still come out defined or every later task that reads them fails. Like `ansible_static`, it re-executes itself inside WSL when `ansible-playbook` is not on the local PATH, through the helper both of them share, [../tier1/wsl_delegate.sh](../tier1/wsl_delegate.sh).
13. `pinned_values` reports fourteen passes across the six assertions that keep the pinned values behind one reader. In order: that the whole set resolved through the shell adapter, which is where a value that is not a string, a reference naming nothing and a reference cycle are refused, with the count in the message and a floor of forty below which the check refuses to mean anything; that all three second-parser needles still match the reader itself, which is the one file the scan excludes and the one file that legitimately names the data file, imports a TOML library and carries a reference-capturing regular expression; how many files were scanned, this check among them, because a guard exempted from itself is a guard nobody checks; that nothing but the reader reads the pins file or resolves a reference; how many `apt_url` and `dnf_url` mapping keys contribute a runtime-built download name; that every pin has a reader or an entry in [../tier1/unread_pins_allowed.txt](../tier1/unread_pins_allowed.txt) with a reason; that the allowlist has no stale entry, meaning one that now has a reader or one naming a pin that no longer exists; that every reader in the three bounded sets names a pin that exists; that no value is empty, because an empty download location makes both dispatch tasks skip without a word; that no value contains a brace after resolution; that every pin answers to the lowercase name the scans reason about; that no pin name is also defined as a variable in any YAML file of the repository; and two from PowerShell, that the adapter hands back as many pins as the reader and that the two agree on every name and value. The reader-set construction is deliberately bounded and the script says how: a reference in the playbook counts only where it is used rather than defined, the dispatcher's runtime-built names are derived from the OS dictionaries rather than grepped for, one pin feeding another is established from the resolved set because this check is not allowed to read the file either, and a bare reference is only treated as a pin reference when it sits in a pin's own name family and is defined nowhere in the repository. The PowerShell half reports SKIP without a runnable `pwsh`, the way `windows_mapping` does and through the same probe. The sibling check [../tier1/pinned_values_reader.sh](../tier1/pinned_values_reader.sh) asks the different question of whether the reader is correct, against fixtures, so nothing here depends on which version is pinned today and a version bump cannot make this red.
14. `pinned_values_reader` reports thirteen passes on the reader itself, which is the question the check above cannot ask: it guards the repository against acquiring a second parser, and this one asks whether the one parser is right. Every adapter is a shim over it, so a wrong answer here is a wrong answer in every runtime at once, and both of the hand-written parsers it replaced would have failed it. Seven fixtures in [../tier1/pins_fixtures/](../tier1/pins_fixtures/) are driven through `INSTALLATION_HELPER_PINS_FILE`, so no case depends on which version is pinned today. All thirteen were proven red by reintroducing the exact defect each one catches into a copy of the reader, and the twelfth proof found a defect in the check itself: the subshell it runs the adapter in returned non-zero under `set -e`, which ended the script before it could report, so a defect killed the check instead of failing it.
15. `manifests` reports four passes on the generated package manifests in `setup/manifests/`, which let a machine be brought up with the vendor's own tooling instead of the whole playbook: that all three files are present, that every one of them still matches what the generator produces from the toggles and the OS dictionaries, that the generator does not open the pinned values file itself because that file has exactly one reader, and that the manifests hold a plausible number of entries rather than being empty, since a generator that produced nothing would agree with empty files and report success. A generated file nobody regenerates is worse than no file: it is committed, it looks authoritative, and it describes the software set as it was months ago.
16. `compose_and_docs` reports that every compose file under `local-dev/` and `homelab/` resolves, that every service in them names an image or a build context, and that every relative markdown link in those two directories points at something that exists. Those two directories are two thirds of this repository and had no test of any kind until 2026-08-21, so a broken compose file or a link left behind by a rename would have shipped unnoticed, and the lowercase markdown rename earlier in this project's history is exactly the change that breaks links quietly. `docker compose config` is asked with `--no-interpolate`, because these files read a secret from a `.env` this repository correctly does not commit and interpolation would fail on its absence while saying nothing about validity. The service question is asked of compose rather than of the indentation: the first version counted every key at two spaces, which catches `volumes:` and `networks:` too, and called three healthy files broken. Absolute links, including `file:` ones, are not followed here. It reports SKIP without a docker binary, because only docker can answer the first two.
17. `network_retries` reports that every task in the playbook that reaches the network carries a retry, or is named in [../tier1/network_retries_allowed.txt](../tier1/network_retries_allowed.txt) with the reason it cannot. It was written after one sweep lost four cells to four unrelated transients on 2026-08-22: a broken pipe from deb.debian.org at file 440 of 440 in a 1.15 GB apt batch, a connection reset from GitHub on one of four font files, an SSL connect error fetching an AppImage inside a flatpak batch, and a TLS eof from python.org on a Python tarball. Two of those are batched calls, so one lost file meant thirty-four applications never installed. A task counts as reaching the network when it uses a fetching module, when its shell body runs one of the fetching commands, or when it unarchives a URL rather than a local file, and it counts as retrying either through the `retries` keyword or through a loop written inside the body of a task launched with `poll: 0`, which the keyword cannot reach at all. An allowlist entry whose task no longer matches the network rule fails the check too, so the file cannot outlive what it excuses. It reports SKIP without PyYAML.
18. `windows_pester` runs the same Pester suite the stage 1 CI job runs, [../tier3/windows/WindowsSoftware.Tests.ps1](../tier3/windows/WindowsSoftware.Tests.ps1), with the Slow and Network tags excluded, and reports its totals. It exists because of what happened on 2026-08-24: the gate here passed 145 assertions, the tree was pushed, and the sweep stopped dead at stage 1 because that suite failed. The plan builder had started reading three optional properties, the suite hands it mappings built by hand without them, and under `Set-StrictMode -Version Latest` reading a property that is not there is a terminating error. Twenty seconds of local Pester would have caught it, and instead the whole matrix was skipped. The totals line is parsed rather than the exit code alone, so a suite that discovered nothing fails this check instead of passing quietly. It reports SKIP without a runnable `pwsh` or without Pester 5, and the CI job stays as well, because that one runs on a clean Windows runner, a state this machine cannot reproduce.
19. `line_endings` reports that none of the tracked text files carries a carriage return, and that `.gitattributes` still declares `* text=auto eol=lf`. The policy has been declared for a while and nothing enforced it in the working tree, which is where it matters: `core.autocrlf=input` normalises on the way into git, so a tree that has drifted to CRLF looks identical in every diff. On 2026-08-22 nineteen files drifted in one afternoon, from edits applied by a script that opened files for writing without naming a newline, and the gate reported three failures that pointed nowhere near it, the loudest being eight registered results supposedly read by nothing. The detection is Python rather than grep, measured rather than preferred: `printf 'a
b
' > f && grep -c $'' f` prints 0 in Git Bash, because its grep strips the carriage return before matching while its awk keeps it, so a grep-based check would pass on exactly the machine that creates the problem. It asks git for the file list, skips anything containing a null byte the way git decides binary, and fails if git lists nothing at all. It reports SKIP without git.
20. `powershell_variables` reports that no PowerShell file under `setup/` reads a variable that nothing in the same file ever assigns. It exists because the Windows settings phase of the sweep of 2026-08-22 died on every run with "The variable '$installationType' cannot be retrieved because it has not been set": the Server SKU change of the day before interpolated that name into the elevated child script it builds and nothing anywhere defined it, and `Set-StrictMode -Version Latest`, which every file here sets deliberately, makes reading an unset variable a terminating error. Nothing else could have caught it. The file parses, PSScriptAnalyzer has no rule for reading an undefined variable, the Pester unit tests never reach that function because it shells out to an elevated child, and the other two Windows checks read the mapping and the toggles rather than this code path. So [../tier1/powershell_variables.ps1](../tier1/powershell_variables.ps1) asks PowerShell's own parser: every `*.ps1` under `setup/` is parsed to an abstract syntax tree, every variable read is collected, and any name that no assignment, parameter, `foreach`, `data` statement or `[ref]` argument in that file binds is reported with its line. Automatic variables are exempt by name, drive-qualified reads such as `$env:PATH` are exempt by definition, and a scope prefix is ignored so `$script:Foo` counts as assigned wherever `Foo` is. It is a per-file question rather than a whole-program one, which is exact today because these files talk to each other through parameters and return values rather than shared state. It reports SKIP without a runnable `pwsh`, the way `windows_mapping` and `windows_settings` do.
21. `ansible_static` reports that `site.yaml` parses, that the syntax check emitted at most two warnings with the actual count in the message, that no repository file is mistaken for an inventory source, that `verify.yaml` parses, that every free-form module body in the tree survives Ansible's own `split_args`, and that the callback keeps both ends of a block it truncates. The last two were added on 2026-08-22 after a day in which the gate passed 139 assertions over a tree that could not run a single Linux install. `--syntax-check` follows `import_tasks` and does not follow `include_tasks`, so a dynamically included file it never opens can be unloadable while the check is green: three apostrophes in a comment inside a shell body, an odd number of single quotes, stopped `pyenv_unix.yaml` from loading at all, because Ansible runs `split_args` over a free-form module argument before anything executes and counts quotes across the whole string, comments included. So every `*.yaml` under `setup/ansible` is walked here, `block`, `rescue` and `always` are descended into, and all 123 free-form bodies go through the splitter, with a file that will not parse as YAML reported by the same assertion rather than skipped. The truncation assertion imports `_truncate_lines` out of [../../setup/ansible/callback_plugins/dual_logger.py](../../setup/ansible/callback_plugins/dual_logger.py), feeds it 500 lines ending in `E: Failed to fetch` and requires that line to survive, because the callback used to keep the first twenty-nine lines of a block and apt says why it failed last. The two expected warnings are correct: no inventory was passed, so only the implicit localhost exists and it does not match `all`. When `ansible-playbook` is not on the local PATH, which is the case in Git Bash on Windows, this script re-executes itself inside WSL rather than aborting the gate.
22. `windows_phase_contract` reports that every Windows phase function returns the summary object its caller reads. `setup.ps1` runs the wizard as a sequence of phases and reads `Results`, `Installed`, `Present`, `Failed` and a few others straight off whatever each phase hands back, under a `Set-StrictMode -Version Latest` that makes a missing property a terminating error rather than an empty value. Commit `fef5e56` removed the Razer Cortex block from the end of `Invoke-WindowsCustomInstall` and took the function's own summary return with it, because the two were adjacent, and nothing noticed: the file still parsed, the Pester suite never calls that function, `powershell_variables` asks about variables rather than return values, and this gate passed 146 assertions over the broken tree. Two Windows cells of sweep 32703419920 then died with "The property 'Results' cannot be found on this object", between the software phase and the settings phase, so a wizard that had installed everything correctly reported none of it and exited non-zero. The check asserts three things per phase function: that it ends on an explicit return with nothing but blanks and comments after it, which is what a deletion of this shape looks like from outside, that the union of properties across its `return [PSCustomObject]@{ ... }` paths covers every property `setup.ps1` reads off the variable it was assigned to, and that the function is findable and closes with a brace in column one. The required property list is read out of the caller rather than written into the check, so adding a `$r.Skipped` to `setup.ps1` without adding `Skipped` to the callee fails here instead of on the next Windows run. Properties are unioned across return paths because a phase may hand back a different shape when it gives up early: `Wanted` exists only on the path where npm is missing, and the caller reads it only inside the `if ($r.NpmMissing)` that path exists to trigger. It is pure text analysis, so unlike the other Windows checks it needs no `pwsh` and never skips.

Optional linters behave asymmetrically on purpose. A yamllint finding fails the gate when yamllint is installed. An ansible-lint finding is printed and never fails. When either tool is missing, the run says so and skips it.

Container limitations do not apply to this capability. No container starts, so nothing in [../tier3/container_limits.yaml](../tier3/container_limits.yaml) is suppressed and neither documented container consequence, the kernel modules that cannot build and the missing login session, is in play here. Those belong to capabilities 30 through 80.

Two coverage gaps that a pass does not close. Tier 1 compares the two wizards against the YAML, but it never runs either wizard's interactive flow, so a defect in the checklist rendering that does not change the parsed key set would not show up. And it asserts that an enabled toggle resolves to a mapping or a task, not that the mapping is correct: a mapping pointing at a package name that does not exist passes here and is caught by capability 20 instead.

## Fixtures

Almost none. The inputs are mostly the working tree itself: [../../setup/setup.sh](../../setup/setup.sh), [../../setup/setup.ps1](../../setup/setup.ps1), the four files under [../../setup/ansible/group_vars/](../../setup/ansible/group_vars/), the five dictionaries under [../../setup/ansible/vars/](../../setup/ansible/vars/), every task file under [../../setup/ansible/roles/](../../setup/ansible/roles/), [../../setup/ansible/site.yaml](../../setup/ansible/site.yaml), [../../setup/ansible/tasks/](../../setup/ansible/tasks/), [../../setup/ansible/profiles/](../../setup/ansible/profiles/), the four native installers under [../../setup/windows/](../../setup/windows/), [../tier1/documented_no_ops.txt](../tier1/documented_no_ops.txt), [../../setup/ansible/verify_install.yaml](../../setup/ansible/verify_install.yaml) and [../tier3/verify.yaml](../tier3/verify.yaml).

The one exception is `os_family_derivation`, which needs an input that is not part of the thing under test: one real `/etc/os-release` per distribution, in [../tier1/os_release_fixtures/](../tier1/os_release_fixtures/). They live beside the check rather than in [../fixtures/](../fixtures/) because they belong to a single tier 1 check rather than to a container capability. Each file carries, in a comment at the top, the archive, packaging repository or forum paste it was taken from, so a reader can re-derive it rather than trust it. Nothing here is written by hand from memory, which matters because a fixture that invents `ID_LIKE` would prove the derivation agrees with the invention.

## Concurrency

- Mutates: none in the repository. Read-only against every input listed under Fixtures. Over-declared because the syntax check touches them: `~/.ansible/tmp` and the fact cache directory named in `ansible.cfg`, both under the invoking user's home.
- Conflicts with: any process editing files under [../../setup/](../../setup/) or [../tier1/documented_no_ops.txt](../tier1/documented_no_ops.txt) while it runs, because the working tree is the input and an edit mid-run produces a result that describes neither the before nor the after state. It conflicts with no other capability test, and it can run alongside any container scenario.
- Serial: false.
