# Tasks allowed to report changed on the second pass of the idempotency scenario, with the reason
# each one cannot be repeatable. Format: <task name exactly as the log prints it> | <reason>
#
# The task name is the whole of what the log puts inside "TASK [...]", which for a role task is
# "<role> : <task name>". Matching is exact and on the full string, so a renamed task drops out of
# this file rather than silently keeping its exemption under the old name, and the scenario fails
# until somebody looks at it again. A line with nothing after the pipe is ignored with a warning
# rather than honoured: an exception with no reason is how an allowlist becomes the place a defect
# hides, which is the one thing this scenario cannot afford.
#
# Before adding a line, decide which of these it actually is.
#
# 1. Genuinely unrepeatable. The task's work is a fact about the moment it ran rather than a state it
#    is converging on. A cache refresh, a timestamp, a temporary file it creates and removes.
# 2. Repeatable, but the task cannot tell. This is a defect in the task, not a property of the work,
#    and the fix is a changed_when or a creates guard on the task rather than a line here.
# 3. Actually doing the work twice. A real bug. It belongs in docs/regression_ledger.md and gets
#    fixed, never allowed.
#
# Only the first kind belongs in this file, and the reason has to say which fact about the moment
# makes it unrepeatable. "Always changes" is not a reason, it is the observation that needs one.

# The first real second pass ran on 2026-08-21 and named twelve. Eight of them are the first kind and
# are below. The other four were the second and third kinds and were fixed instead.
#
# Four create-and-remove pairs, all deliberate. Each one exists because the run must not leave
# something behind, so the second run necessarily recreates what the first one cleaned up. That is
# the definition of unrepeatable work rather than a task that cannot tell.

# The escalation the playbook grants itself and then takes away again. Leaving it in place would mean
# every run ends with NOPASSWD: ALL still on the machine, which the ledger already has an entry for.
debian_core : Configure passwordless sudo for non-root user (Debian/Ubuntu) | the entry is removed in the always block at the end of every run, so the next run has to write it again
arch_core : Configure passwordless sudo for non-root user | the entry is removed in the always block at the end of every run, so the next run has to write it again
Remove the temporary passwordless sudoers entry (Linux) | it removes what this run created, and there is always something to remove

# The staging directory for downloaded installers, created at the start and deleted at the end so a
# vendor archive is never left lying in a predictable path.
system_core : Ensure temporary installation folder exists | it is deleted in the post-tasks of every run, so the next run has to create it again
Remove temporary installation folder | it removes what this run created, and there is always something to remove

# Two vendor archives that are downloaded, installed from, and then deleted on purpose, because a
# kept copy becomes a cache that a version bump cannot invalidate.
software_installer : Download Gridcoin flatpak bundle (Linux) | the bundle is deleted after installation, so it is absent at the start of every run
software_installer : Remove the staged Gridcoin flatpak bundle (Linux) | it removes what this run downloaded, and there is always something to remove
software_installer : Download GpuTest binary archive | the archive is deleted after extraction, so it is absent at the start of every run
software_installer : Remove the staged GpuTest archive | it removes what this run downloaded, and there is always something to remove

# The third staged archive, and the same shape as the two above. I called this one a genuine
# offender at first and it is not: get_url does not re-download a file that is already there, and
# the reason it is not there is that the post-tasks deleted the whole staging directory on the
# previous run. The correction matters, because the fix for the second kind is a guard on the
# task and the fix for this kind is a line here.
software_installer : Download Antigravity Linux tarball | the tarball lives in the staging directory the post-tasks delete, so it is absent at the start of every run

# The Dart SDK zip on Fedora, the same create-and-remove pair as the three above, found by the first

sdk_manager : Download Dart SDK zip (Fedora) | the zip is deleted after extraction, so it is absent at the start of every run
sdk_manager : Remove the staged Dart SDK zip (Fedora) | it removes what this run downloaded, and there is always something to remove

# The vendor .deb staging pair, the last of this family, found by the Ubuntu idempotency run on
# 2026-08-21. Debian reported none of these because its first pass failed early and the second pass
# never reached them, which is worth knowing: a clean second pass after a failed first pass is not
# the same evidence as a clean second pass after a clean first one.
software_installer : Download .deb files for apt_url installs | the files live in the staging directory the task below deletes, so they are absent at the start of every run
software_installer : Remove the staged vendor .deb files | it removes what this run downloaded, and there is always something to remove

# The AppImageLauncher RPM staging pair on Fedora, the last of this family. The install between them
# is NOT here: its creates guard named a lowercase path the package never writes, which is a defect
# in the guard and was fixed rather than excused.
software_installer : Download AppImageLauncher RPM (Fedora) | the RPM is deleted after installation, so it is absent at the start of every run
software_installer : Remove the staged AppImageLauncher RPM (Fedora) | it removes what this run downloaded, and there is always something to remove

# A full system upgrade on a rolling distribution, which is the one task here that is honestly
# allowed to do work on a second pass. Arch and CachyOS publish packages continuously, and the two
# passes of this scenario are separated by the length of a full install, so a newer build landing in
# between is ordinary rather than exceptional. It reported changed on 2026-08-22 for exactly that
# reason, having reported nothing on the same tree the day before.
#
# The alternative would be changed_when: false on the task, and that would be a lie: it really did
# upgrade packages. The database refresh next to it is a different case and is already false, because
# refreshing an index is an act rather than a state.
arch_core : Upgrade the system (Arch) | Arch and CachyOS are rolling, so a newer package between the two passes is normal and upgrading it is real work rather than a repeated one
