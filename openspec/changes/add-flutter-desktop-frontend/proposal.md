## Why

Today the only way to use this toolkit is a terminal: [setup/setup.sh](../../../setup/setup.sh) on Linux and macOS, driven by gum screens, and [setup/setup.ps1](../../../setup/setup.ps1) on Windows, driven by Out-ConsoleGridView. Both need the repository on disk first, and on a fresh machine that means installing git, cloning, and knowing which script to start in which shell. The owner decided on 2026-10-10 to add a desktop front end in the spirit of Chris Titus WinUtil: download one file from the GitHub releases of Lukk17/InstallationHelper, double-click it, tick boxes, follow the progress, read the final summary.

The scripts stay the single source of truth. The front end never reimplements install logic, never decides on its own which toggles exist, and never runs anything the scripts would not run from a terminal. A machine with no screen keeps working exactly as it does today. This matters because two of the defect classes recorded in [AGENTS.md](../../../AGENTS.md) are exactly what a second front end invites: the same rule implemented in two places that then disagree (class 2), and a second entry point drifting from the primary one (class 7).

## What Changes

1. A new Flutter desktop application under a new top-level directory, [desktop/](../../../desktop/), for Windows, Linux and macOS. It reads the toggle catalogue from the scripts, lets the user choose, shows the exact command the script will run, runs it over a hidden pseudo terminal that the user never sees, shows a progress list with one row per step and per package and its status, keeps the raw output behind a "Show details" button as plain read-only text, answers the script's own password prompt, reboot question and any unexpected question through its own dialogs, and ends on a summary built from a result file the script writes. The owner decided on 2026-10-11 that the application never shows a terminal.
2. The application runs as the normal user and never as administrator or root, on every platform. On Windows its manifest stays `asInvoker` and [setup/setup.ps1](../../../setup/setup.ps1) keeps elevating itself, so Windows shows its own User Account Control prompt and the application never handles an administrator password. For a run the application starts, that is one prompt per run through one elevated helper, decided by the owner on 2026-10-11 (design decision 8 item 6), while the terminal wizard keeps one prompt per elevated step. On Linux and macOS the script keeps asking for the sudo password itself, through the hidden pseudo terminal, with no change to that code path. The application recognises each prompt, as often as it appears in one run, and shows its own password dialog whose input is written to that hidden channel and is never stored or logged.
3. Machine-readable output added to both wizards, so the application reads the same lists the wizards already build rather than parsing their human output or the YAML files:
   1. `setup.sh --list-software --json` and `setup.ps1 -ListSoftware -Json`: the selectable toggles with key, label, default state and group.
   2. `setup.sh --list-profiles --json`: the profiles under [setup/ansible/profiles/](../../../setup/ansible/profiles/) with name, description and the toggles each one overrides. Windows has no profiles that apply, which [setup/setup.ps1](../../../setup/setup.ps1) already states.
   3. `setup.sh --result-file <path>` and `setup.ps1 -ResultFile <path>`: a JSON file written at the end of a run with the exit code, the per-phase outcome and the per-application verification verdicts.
   4. A JSON schema for each of these under a new [setup/contract/](../../../setup/contract/) directory, checked by new tier 1 checks on both wizards.
   5. `setup/contract/interactive_prompts.json`, the list of every question `setup.sh` can ask, with a tier 1 check that fails when a new interactive `read` in setup.sh is missing from it, so the application can never meet a question it does not know.
4. The scripts ship inside every artifact, taken with `git archive` from the same commit as the release tag, and are unpacked at first start into a per-user, per-version, writable directory that the host can see. One code path for every package format, including the Flatpak, where the host cannot see `/app`.
5. Self-distributed artifacts on GitHub releases, no store submission:
   1. Windows: an Inno Setup installer `.exe` that installs for all users by default, with an install mode dialog and a `/CURRENTUSER` switch for the current user only, a portable `.zip`, and a local winget manifest offering both scopes. The administrator prompt appears only while installing, and the installed application still runs as the normal user.
   2. Linux: a `.tar.gz` of the Flutter bundle, an AppImage, a Flatpak single-file bundle, a signed Flatpak repository on GitHub Pages so `flatpak update` works, and a classic Snap installed locally with `--dangerous --classic`.
   3. macOS: the `.app` in a `.dmg` and a `.zip`, plus a Homebrew cask in a `Casks/` folder at the top level of this repository, tapped with `brew tap Lukk17/installationhelper https://github.com/Lukk17/InstallationHelper` and installed with `brew install --cask Lukk17/installationhelper/installation-helper`. Unsigned, with the Open Anyway steps in the README.
6. A new release workflow, [.github/workflows/desktop-release.yml](../../../.github/workflows/desktop-release.yml), `workflow_dispatch` only, because [AGENTS.md](../../../AGENTS.md) forbids any workflow that starts on push or any other automatic event. It builds every artifact on Windows, Ubuntu and macOS runners, smoke tests each one by launching it, and uploads them to a draft GitHub release, together with the Homebrew cask filled with the new version and SHA-256. It never commits or pushes: after publishing, the owner commits that cask file to `Casks/installation-helper.rb` on `master` himself. Release tags are `vX.Y.Z`, equal to the application version.
7. A second new workflow, [.github/workflows/desktop-flatpak-pages.yml](../../../.github/workflows/desktop-flatpak-pages.yml), also `workflow_dispatch` only, that signs the Flatpak of a published release into an OSTree repository with a GPG key the owner generates, and deploys it with its `.flatpakrepo` and `.flatpakref` files to GitHub Pages.
8. A full "Install the desktop app" section in [README.md](../../../README.md) with every command for every format, PowerShell and Unix shell forms, plus a new hub page [desktop/README_DESKTOP.md](../../../desktop/README_DESKTOP.md). Both explain in plain words how the application asks for passwords on Linux and macOS (the user never sees a terminal, and the password goes into the application's own dialog and is never stored) and for administrator rights on Windows (Windows' own User Account Control prompt, which the application never sees).

Nothing here is breaking. Every existing option, exit code and output of both wizards keeps its meaning. The new options are additive and refused in combinations they do not support, which is the repository's existing rule for unknown input.

## Capabilities

### New Capabilities

- `desktop-app`: what the desktop application does from start to finish: the prerequisite check, loading the catalogue from the scripts, the selection, the preview, the run over a hidden pseudo terminal shown as a progress list, the dialogs for the password, the reboot question and unexpected questions, cancel, the summary, and the privilege rule.
- `wizard-machine-output`: the JSON listing, profile listing and result file both wizards gain, their schemas, and the parity both wizards must keep with each other and with their existing text output.
- `desktop-distribution`: what each release artifact contains, how each one is installed, the bundled scripts matching the release tag, the dispatch-only release workflow, the signed Flatpak repository on GitHub Pages and its dispatch-only deployment, and the smoke test every artifact must pass before it is attached to a release.

### Modified Capabilities

None. [openspec/specs/](../../specs/) holds no capability yet, verified with `openspec list --specs` on 2026-10-10.

## Impact

1. New directory [desktop/](../../../desktop/): the Flutter project, its tests, and the packaging configuration for every format.
2. [setup/setup.sh](../../../setup/setup.sh): new options `--json`, `--list-profiles` and `--result-file`. The interactive path and every existing option are untouched.
3. [setup/setup.ps1](../../../setup/setup.ps1) and [setup/windows/WindowsVerify.ps1](../../../setup/windows/WindowsVerify.ps1): new parameters `-Json` and `-ResultFile`.
4. [setup/ansible/verify_install.yaml](../../../setup/ansible/verify_install.yaml): writes the per-application verdicts to a JSON file when the wizard asks for one. This triggers the forced-failure container scenario under the [AGENTS.md](../../../AGENTS.md) table.
5. New [setup/contract/](../../../setup/contract/) with three JSON schemas and the inventory of interactive prompts.
6. New tier 1 checks under [e2e/tier1/](../../../e2e/tier1/) and new Pester tests in [e2e/tier1/windows/](../../../e2e/tier1/windows/).
7. New workflows [.github/workflows/desktop-release.yml](../../../.github/workflows/desktop-release.yml) and [.github/workflows/desktop-flatpak-pages.yml](../../../.github/workflows/desktop-flatpak-pages.yml), plus a tier 1 check that every workflow in the repository is dispatch-only or call-only.
8. Documentation: [README.md](../../../README.md), [AGENTS.md](../../../AGENTS.md) ("What This Repo Is", the hub list and the CI section), [setup/README_SETUP.md](../../../setup/README_SETUP.md), new [desktop/README_DESKTOP.md](../../../desktop/README_DESKTOP.md), and [docs/regression_ledger.md](../../../docs/regression_ledger.md) for every defect found along the way.
9. A new top-level `Casks/` folder holding `Casks/installation-helper.rb`, which makes this repository the Homebrew tap, as the owner decided on 2026-10-11 (design decision 12.5). No second repository. The consequences the owner accepted: every user types the URL in the tap command, every release needs a follow-up commit on `master` that updates the cask's version and SHA-256, and tapping clones this whole repository. A new tier 1 check keeps the committed cask equal to its template and the repository root free of `.rb` files.
10. GitHub settings the owner changes by hand, once: GitHub Pages enabled with the source "GitHub Actions", which creates the `github-pages` environment, and two environment secrets on it, `FLATPAK_GPG_PRIVATE_KEY` and `FLATPAK_GPG_PASSPHRASE`, holding the Flatpak signing key and its passphrase. The owner generates that key on his own machine, an Ed25519 signing key with the user id `Lukk17 <luksarna@gmail.com>`. The public key is committed under [desktop/](../../../desktop/), the private key never is. The key has no expiry date, decided by the owner on 2026-10-11, and a documented revocation and key rotation procedure replaces the expiry, design decision 12.6.
11. New build-time dependencies, none of them in the shipped artifacts except the Flutter runtime: Flutter 3.47.7, Fastforge 0.6.12, Inno Setup 6, appimagetool, appdmg, snapcraft 9.1.4, flatpak-builder, and in the Pages workflow flatpak and GnuPG. Runtime Dart packages are listed in design decision 4.
12. Artifact sizes grow by about 29 MB each over the owner's first estimate, because the scripts directory is 29.9 MB compressed, measured with `git archive --format=tar.gz HEAD setup | wc -c` on 2026-10-10. 18 MB of that is [setup/config/lukk_desktop_profile.knsv](../../../setup/config/lukk_desktop_profile.knsv) and 13 MB is [setup/wallpapers/](../../../setup/wallpapers/). The owner decided on 2026-10-11 to bundle all of it, so every artifact works offline.
